# Modern Warfare Remastered (H1, PC x64) zones

`crates/fastfile_h1` reads Modern Warfare Remastered zones and Horizon MW's
usermaps (maps built with the x64 zone tools for H1): container, asset list,
the exact asset walk, and a map reader (`map.rs`) whose API mirrors
`fastfile_iw6::map`.

What was checked, and on what: every walk below ends **exactly** (stream
position = inflated image length, VIRTUAL offset = the XFile's VIRTUAL block
size, 0 unresolved references):

## Container (`container.rs`)

Advanced Warfare's envelope with version `0x42`:

```
0x00 "S1ff0100" (retail, signed) | "S1ffu100" (tools, unsigned)
0x08 u32 version = 0x42
0x0c u8 compress = 1, u8 compressType (4 = LZ4 retail, 1 = zlib tools), u8 8, u8 4
0x10 u32 fileTimeHigh, u32 fileTimeLow
0x18 u32 imageCount, then imageCount x XStreamFile (24 bytes):
     +0 u16, +2 u16 file index, +4 u32, +8 u64 offset, +16 u64 offsetEnd
     u64 baseFileLen, u64 totalFileLen
retail: "S1ffs100" auth header, data from +0x8000 in 0x800000-byte runs each
        followed by a 0x4000-byte hash block; data = u64 size, u32 flags,
        then { u32 packed, u32 size, LZ4 block } padded to 4
tools:  one zlib stream right after the two lengths
```

## Streamed images and paks (`image.rs`)

A streamed image takes four `XStreamFile`s from the header table, in walk
order. Each names `offset..offsetEnd` of a pak. The bytes there are packed as
the zone data is (u64 size, u32 flags, LZ4 blocks), in tools' paks too.

* **Retail:** file index N means `zone/imagefile<N>.pak`.
* **Tools (usermaps):** file index **96** means the zone's own pak,
  `<zone>.pak` beside the `.ff` (x64-zt `h1/zone.cpp`
  `CUSTOM_IMAGEFILE_INDEX 96`; `utils/imagefile.hpp` writes
  `<fastfile>.pak`). Evidence: mp_rust's 254 index-96 entries end at
  0x3d2cfcc = the size of `mp_rust.pak`, and all 65 index-96 images read.
  A usermap's other streamed images name retail paks by index (mp_rust: 53
  images over `imagefile1`, `3`, `5`, `6`, `7`, `9`, `11`, `13`, `19`, `21`,
  `46`, `55`); they need the game's own `zone/` folder.

`ImagePaks::for_zone(zone_path, retail_dir)` resolves both.
`ImageRec::stream_files[k].file_index` keeps the index, and
`map::Summary::images_in_zone_pak` counts the own-pak images.

## The walk: H1 against S1 (Advanced Warfare)

H1 is S1's engine with its own struct layouts. Walkers changed from S1's:

* **Technique sets:** 240 techniques (S1: 180).
* **Tools' stale pointers:** x64-zt's H1 writers forget `clear_pointer` in a
  few places (technique pass `args`, model surface tables), so the field holds
  the tool's own heap address (`0x0000_02xx_xxxx_xxxx`) while the data still
  follows right there. `Stream::ptr_at` reads any non-zone value in a pointer
  field as "follows". Retail zones never have such values, and
  `Stream::raw_ptr_at` gives the value as stored.
* **Weapon:** 190 animations ×3 (right, left, normal), 64 reticle view
  models, notetrack hide tag tables, raise sounds before the alt switch
  sounds, separate knot counts for the original accuracy graphs.
  **Attachment:** 64 reticle view models, bounce and rolling sounds per
  surface type (53), hide and show tags. Checked on retail `common_mp`
  and on Horizon MW's four weapon zones.
  **Original accuracy graph knots** are sized by `accuracyGraphKnotCount`,
  not by `originalAccuracyGraphKnotCount`: they are a copy of the knots.
  Horizon MW's `at4_mp` (hmw_ar1) stores 3 + 2 original knots with
  `originalAccuracyGraphKnotCount` = 0, 0. Wherever both counts are set,
  in every other zone, they are equal. Reading 0 knots left 40 bytes
  unread, and hmw_ar1 stopped at asset 711, two weapons in.
* **Effects:** each visual of a decal element is **three** materials
  (`FxElemMarkVisuals`: `mc/`, `wc/` and `wc/..._autodisplacement`). S1 and
  Ghosts have two. Reading two drifted retail common_mp by 8 bytes per
  decal visual, starting at its first impact effect (asset 4205), until the
  walk ran off the zone. None of the tools' zones that walked had decals.
* **Equipment sound table:** in retail common_mp the table
  (`soundaliases/equipment_snd.def`) is only its name: no counts, every
  pointer null, and the next asset follows the string. The walker reads
  exactly that. A filled table still falls back to "run to the next asset",
  because there is no reference layout (x64-zt writes the name only).
* **Menus:** `MenuList` and `menuDef_t` have Ghosts' shape (ported from
  `fastfile_iw6::walk::menu`). S1's heuristic "run to the next asset" is
  gone.
* **New:** leaderboard (columns: name, stat name), TTF (`fileLen + 1`
  bytes), and every map asset (`walk/world.rs`).

### Map assets (`walk/world.rs`)

These started from Ghosts' walkers. H1 changes:

* **PathData:** nodes with their links, vis bytes, node trees (a leaf holds
  u16 node indices; an inner node's two children follow recursively, each
  aligned 4), dynamic node groups, then exposure / no-peek vis / zones /
  dynamic states bytes.
* **FxWorld:** initial geometry is written *before* the initial piece
  states (Ghosts: after). Glass defs: physics preset, the two materials,
  four effects, three sound name slots. (The preset used to be read after
  the materials; it only matters when a map defines its own, inline, instead
  of referencing a shared zone's: `mp_countdown` and `mp_creek` do, and the
  wrong order stopped their walks at the next image. Both now walk exactly
  (3841 and 4290 assets) and `h1_map_top` draws a recognisable map: Creek
  380/380 spawns over a drawn surface, 100 % of the frame; Countdown 383/383,
  98 %. `mp_bloc` and `mp_broadcast` still walk exactly. `h1_walk_check
  <zone.ff>` prints walked count, stream position against zone size.)
* **GfxWorld:** Ghosts' order plus portal groups and portal distance anchors
  after the cells, plane lists on reflection probe volumes, displacement
  parameters (aligned 64) after the indices, three light grid trees, static
  visibility with 27 + 27 "unknown" and 4 + 4 umbra arrays (all RUNTIME
  except `unknownSModelVisData1/2`, which are in the file:
  4 × and 8 × `smodelVisDataCount` bytes, aligned 128), static model lighting
  split out of the draw instances (`smodelLightingInsts`, 24-byte union;
  vertex lighting values only for draw flag 0x80), subdivision vertex
  lighting, MDAO volumes, then the four build info strings.
* **MapEnts:** H1 adds light set, colour lookup, context, water and one
  unknown client trigger table. The writer's order puts `unkTriggers`
  after `blendLookup`, not in struct order.
* **GlassWorld:** pieces and names, as Ghosts'.
* **PhysWorld** (new in H1): brush models, polytopes (as PhysCollmap's),
  meshes (nodes aligned 16, vertices aligned 16, triangles), water volumes
  (each names a PhysWaterPreset).
* **clipMap_t:** the `ClipInfo` now holds the terrain (verts, tri indices,
  walkable edge bits, borders, partitions), the AABB trees and the static
  model placements. Brush sides name their plane by **index**
  (`cbrushside_t`, 8 bytes; Ghosts: a pointer). The map has nodes, leafs,
  cmodels (`cmodel_t::info`: the tools point every sub-model at the map's
  `pInfo`), stages, stage triggers, dynamic entities (H1 adds a sound),
  scriptable instances (event constants, H1 target data, RUNTIME part states
  and event stream) and the grapple magnet tree.

## World data (`map.rs`)

* **World vertex:** 44 bytes, Ghosts' layout. Normal and tangent are
  unsigned 10:10:10 over 1023. On mp_rust and mp_courtyard_ss the mean
  unit length is 1.000 read that way and 1.2–1.3 read signed.
* **Surfaces:** H1 groups the world vertices in blocks of at most 65536.
  Every surface of a block has the block's `firstVertex` and `vertexCount`
  (mp_rust: 5 blocks over 235,386 vertices; mp_courtyard_ss: 8 over 349,682),
  and its indices count from `firstVertex`. Measured: no index of any surface
  reaches its block's `vertexCount`, and the largest is 58495 / 65357. The
  `srfTriangles_t` has an extra `int` before the counts (vertexCount at +16,
  triCount +18, baseIndex +20). The vertex for index `i` is
  `first_vertex + i`, as Ghosts'.
* **Static models:** placement and model are in the 80-byte draw instance.
  Flags 0x20 ground lit, 0x40 light grid, 0x80 vertex lit, 0x100 model
  lightmap. Ground lighting is four half floats in the lighting union.
* **Lightmaps:** primary `R8_UNORM` (DXGI 61) on the usermaps,
  `BC4_UNORM` (DXGI 80, as Ghosts') on the retail maps; secondary
  `R16G16B16A16_FLOAT` two pages stacked (DXGI 10). Inline in the zone on
  both usermaps and on Shipment (3 pages: 2048x4096, 2048x2048,
  1024x2048 primaries).
* **Entities:** the usermaps' entity string has named keys (`"classname"
  "worldspawn"`); a retail map's has numbers (`170 "worldspawn"`), as
  Ghosts'. `map::H1_KEYS` names them (see *Retail maps*). The usermaps
  keep their spawns both in the text and in `spawnList` (44-byte records,
  H1 adds `targetname`); Shipment only in `spawnList`.
  `IwMap::entity_string()` writes a record as an entity only when the text
  lacks it (same classname and origin).
* **Sun:** the first primary light of type 1 (`ComPrimaryLight`, 144
  bytes in H1).

## Retail vs tools

Differences seen or expected between the game's own zones and the tools':

* **Container:** retail is signed with LZ4 blocks; tools are unsigned with
  zlib.
* **Stale tool pointers:** the tools leave heap addresses in some pointer
  fields (above); retail does not.
* **Paks:** retail streams from `imagefile<N>.pak` only. Tools add
  `<zone>.pak` as index 96.
* **Sub-assets:** the zone tools always write a sub-asset (material, image,
  model of a world) as a reference to the table asset. Retail zones may load
  some inline (S1's, IW6's experience: vehicles' turret weapons, scriptable
  defs inside clip maps). The walker handles both forms everywhere it reads
  an asset pointer (`Walker::asset`).
* **Fields the tools null:** `cmodel_t::info` (tools: the map's `pInfo` by
  reference; a retail map could carry its own inline `ClipInfo`, which is
  read if present), scriptable instances whose def is missing (tools zero the
  whole instance).
* **Entity keys:** retail maps number them (`map::H1_KEYS`); the tools
  write names.
* **Placeholders:** retail `common_mp` writes 2606 materials (all of them),
  78 models and 24 images as a header that holds only a name with a leading
  `,` (`,wpn_h1_asl_ak47_vm_camo`, `,$white`). Every other field is zero
  and nothing follows. The asset's data is in another zone loaded with this
  one, and the game binds by name. The tools' zones have none. A retail
  map zone's materials are all placeholders too (*Retail maps*).

## Retail maps

Read on `mp_shipment` with the zones the game loads beside it
(`cargo run -p fastfile_h1 --release --example h1_retail -- <map.ff>
<zone.ff>...` prints what each zone holds of what the map names).

* **Materials are names.** `mp_shipment.ff` has 904 materials, every one a
  placeholder (`,wc/...` world, `,m/...`/`,ml/...` model, `,*0_1n`
  blended layers); its world and placed models use 771 of them. Their
  definitions are in **`techsets_<map>.ff`** beside the map (Shipment:
  1425 materials, 887 full, 770 of the 771), as IW7's maps, and one in
  `techsets_common_mp.ff`. `common_mp`'s 2606 materials are all names,
  `patch_common_mp` has 7694 full ones (one of Shipment's is there too).
  The definitions name their pictures only (`,hms_brick_brown_a_col`).
  Technique set names have no `wc_` prefix (`l_sm_lmpb_r0c0_b1c1sl1_nfwpf`);
  they are read by their tokens, as Ghosts'.
* **Pictures are the map's.** Every picture Shipment's definitions name is
  in the map zone itself (1970 images: 56 inline, 1491 streamed from the
  retail `imagefile<N>.pak`s, 423 names), except 7 in `common_mp` and the
  engine's in `code_post_gfx_mp` (`h1_og_shadow`, the BRDF table
  `~envbrdflut_ggx_16-rg`). `patch_common_mp` holds none of them.
* **Order.** The game loads `code_post_gfx_mp`, `common_mp` and its
  techsets and patch, then the map's techsets, the map and the map's patch;
  an asset of a name in a later zone replaces the earlier one. So a
  material is taken from the first of `patch_<map>`, `techsets_<map>`,
  `patch_common_mp`, `techsets_common_mp` (then the core zones), a picture
  from `patch_<map>`, the map, `patch_common_mp`, `common_mp`,
  `code_post_gfx_mp` (`shared::retail_zones`; `patch_mp_shipment`'s 19
  full materials and 56 pictures replace none of Shipment's).
* **Memory.** `patch_common_mp` inflates to 628 MB (525 MB of inline
  pictures), `common_mp` to 1354 MB (304 MB). `shared::Wanted` lists what
  the map's world and placed models need (the placeholders, then the
  pictures the definitions name that the map does not hold);
  `SharedImages::add_zone_for` keeps only those, the material-only zones
  read first so every material is chosen before its pictures are looked
  for, each zone dropped when read, and a zone that could add nothing more
  not opened. Shipment keeps 771 materials and 9 pictures (117 KB); the
  peak while `common_mp` is open is 2.1 GB (the map's 350 MB zone, the
  file and its inflated image).
* **Compass.** The map's `compass_map_<map>` material (a placeholder,
  defined in `techsets_<map>`) names `h1_og_compass_map_<map>` (in the
  map, 1024x1024). The corners are two `script_origin`s with
  `targetname` `minimap_corner` in the numbered entity text.
* **Entity keys.** Numbers, the canonical script strings, in alphabetical
  order of their names: `angles` 65, `classname` 170, `height` 488,
  `model` 668, `origin` 738, `radius` 849, `script_label` 916,
  `script_linkname` 918, `script_noteworthy` 920, `spawnflags` 986,
  `suncolor` / `sundirection` / `sunlight` 1046-1048, `target` 1188,
  `targetname` 1190, `_color` 1395, `script_gameobjectname` 31220,
  `script_linkto` 31270 (read off Shipment's and Crash Snow's values; the
  same numbers on both). Key `0` is followed by a named key
  (`0 "node_name" "..."`). Others stay `h1_<number>`. Before this, no
  retail map entity had a classname: Shipment's 12 brush models were not
  placed and its corners were not found.
* **Spawn points in the air.** 193 of Shipment's 366 spawn records stand
  65 to 96 units above the ground: every `*_overflow` start (z 287), most
  axis starts (z 262), some TDM and DM points. The drawn world under them
  is the ground at z 192 and nothing between, and the collision's floor is
  that ground: the map's authors placed them there, and `placespawnpoint`
  drops them to it (H1's and Black Ops II's). Not an offset or collision
  bug. The lane's `h1 spawn floors` line tells these from a point over a
  drawn floor the collision lacks (0 on all three maps).
* **Not staged here:** the retail `imagefile<N>.pak`s (Shipment names 21
  of them), and `techsets_mp_crash_snow` / `patch_mp_crash_snow` (without
  them Crash Snow's 3520 materials are names only, and it draws grey).

## Guns

`h1_guns` lists every weapon in a zone: name, display name (the localize
key and, with `--strings`, its English text), type and class, view, world
and hands models, animations, attachments, and where the models, images and
sounds are. Run on the two zones there are:

```
cargo run -p fastfile_h1 --release --example h1_guns -- \
  --strings zone/english/eng_patch_code_post_gfx_mp.ff \
  --strings hmw-mod/zone/eng_hmw_common.ff \
  hmw-mod/zone/hmw_shotgun.ff zone/common_mp.ff
```

### What a gun lane reads

```rust
let zone = fastfile_h1::Zone::open(path)?;
let (cap, stop) = fastfile_h1::walk::walk_zone(&zone); // stop: None when exact
for g in &cap.weapons {              // WeaponRec
    g.name; g.display_name;          // cap.localize[&g.display_name] when the zone has it
    g.def.get(&zone.image);          // the WeaponDef bytes, at layout::WeaponDef offsets
    g.gun_models[0]; g.world_models[0]; g.hand_model; // Option<AssetId> of an XModel
    g.anims;                         // 190 slots (also anims_right / anims_left): XAnimParts
    g.attachments;                   // AttachmentRec ids: fields, view and world models
    g.sounds;                        // (WeaponDef offset, alias name) -> cap.sounds
    g.fx; g.models; g.materials; g.tracer; g.anim_overrides; g.notetrack_sound_keys;
}
cap.xmodels[id.index]                // bones, tag positions, materials, lods, composite parts
cap.model_surfs[..].surfs            // verts (32-byte GfxPackedVertex), tris, rigid and blend
cap.materials[..].textures           // image ids and the techset
cap.images[..]                       // inline pixels, or stream_files -> image::image_pixels
cap.xanims[..]                       // frames, indices and data spans in the zone image
cap.sounds / cap.loaded / cap.sound_files // alias -> SoundFile -> LoadedSound (inline or pak)
```

`image::ImagePaks::for_zone(zone_path, Some(retail_zone_dir))` resolves
both the zone's own pak (index 96) and the retail `imagefile<N>.pak`. A
name that starts with `,` is a placeholder: bind it by name (without the
comma) to the same asset in another zone.

## Guns in game (`assets::lane::hmw`)

Horizon MW's guns are guest guns in a Black Ops II match, under their own
namespace (`AssetNamespace::H1`, prefix `h2_`): `h2_ak47_mp`, `h2_at4_mp`
(the zone's `at4_mp`). Create-a-Class lists them on an **MWR** tab (it
replaces the "coming soon" placeholder).

* **Roster:** `bo2_profile::guest::HMW`, 46 guns, statstable rows from
  `HMW_FIRST_INDEX` (1300). Assault rifles ak47, fal, famas, fn2000, m16,
  m4, masada, scar, tavor; SMGs ak74u, kriss, mp5k, p90, ump45, uzi; LMGs
  aug, m240, mg4, rpd, sa80; snipers barrett, cheytac, m21, m40a3, wa2000,
  mors; shotguns aa12, m1014, spas12, striker, winchester1200, and ranger
  and model1887 as secondaries (as MW2's); pistols pp2000, glock,
  beretta393, tmp, usp, coltanaconda, m9, deserteagle, colt45, boomhilda;
  launchers at4, rpg, m79. One description line each (`GUN_LINES`,
  `h2_<gun>`), "From Horizon MW."
* **Not listed:** `h2_infect_mp` (the Infected mode's weapon), Semtex,
  the throwing knife, and the melee weapons (hatchet, shovel, sickle,
  karambit "Diabolical", icepick "Cliffhanger"): no other guest game lists
  its melee weapons, so they wait for a melee slot. `hmw_attachments` is
  therefore not read.
* **Listed beside the others:** Horizon MW's guns are their own guns.
  `listed()` takes them once among themselves (`BESIDE`), so `h2_m4`
  appears next to MW2's `mw2_m4`, MW3's and CoD4's; the `mw2_*` rows are
  exactly what they were. Black Ops II's own gun of a name (its SCAR-H)
  leaves the HMW copy out, as it does MW2's. The @leetinservers mod's
  copy of an HMW gun (its Boomhilda, its MORS) gives way to it, as it
  does to any game's.
* **Where:** `asset_audio::hmw_zone_dir()`: `CODLEGACY_HMW_ZONE`, else the
  `mwr` game folder's `hmw-mod/zone`. The front end lists the tab when a
  weapon zone is there; the match keeps it when the guns loaded.
* **Build:** each zone walked, built, dropped in turn (about 3 s each in
  release; the peak is one zone). A gun's `WeaponDef` is laid out as AW's
  (`lane::hmw_fields`, every field both layouts have, generated from
  them) and goes through `WeaponCatalog::capture_s1`: Black Ops II
  gunplay as AW's guns get. Animation slots are AW's but for H1's
  inspection slot (112), after which H1's numbers are one higher. Empty
  stub animations (0 frames, no bones) leave their slot empty. Composite
  models join their parts on the receiver's bone of the part's root name.
  Materials and pictures are `H1Builder`'s, in the H1 namespace with
  their own names. Effects (`FxCatalog::capture_s1_in`) and tracers
  (`TracerCatalog::capture_s1_in`) are AW's records; distortion, blur and
  lens-dirt visuals are left out. Arms are Black Ops II's.
* **Default scopes:** a Horizon MW sniper's scope is not part of its gun
  model and not in its `WeaponDef.attachments` list. It is an attachment of
  its own, `<gun>scope` (`cheytacscope`, `barrettscope`, `m21scope`,
  `m40a3scope`, `wa2000scope`, `morsscope`), with
  `WeaponAttachment.automaticAttachment` set: the game puts it on the weapon
  by name. Its `viewModels[0]` / `worldModels[0]` are made at their origin
  with the root bone `tag_scope`, which the gun's models have. The lane
  finds the zone's automatic `<gun>scope` that has a view model and hangs
  its view model, and its world model, on `tag_scope`
  (`guest_attach::own_scope` → `give_guest_scope`). Where the gun's world
  model is a composite that already holds the scope (`h2_weapon_cheytac`,
  `attach_m40a3_npc`, `h2_weapon_wa2000`), the world model is not added a
  second time. The attachment's `hideTags` / `showTags` are walked
  (`AttachmentRec::hide_tags`, `show_tags`), and an attachment's hide tags
  go on the variant. None of the six scopes hide anything; the gun's own
  `hideTags` (`tag_sight_off`, the MORS's `tag_ironsight`) apply as before.
  Aimed, the gun shows Black Ops II's sniper scope ([SCOPES.md](SCOPES.md)),
  and a sight variant (ACOG, thermal) takes the scope model off.
  Composite parts that show by default (bipods of the Barrett and M21, the
  Boomhilda's scope) are joined into the gun model.
* **Gun-specific sights are not defaults:** `augscope` (the AUG's ACOG,
  `WEAPON_ACOG_ATTACHMENT`) and `f2000scope` (the F2000's "Red Dot
  Sight") are in the gun's list and not automatic. They are offered as the
  sight their display name gives (`acog`, `reflex`). The AUG used to wear
  its scope all the time and aim through a sniper scope.
* **Sounds:** `asset_audio::sound_load_h1`, inline in the zones: 16-bit
  PCM, and FLAC kept whole (`H1_FLAC`) and decoded by `audio`'s clip
  store when played.
* **Pictures:** CaC: the original game's Create-a-Class picture of the
  gun, read as that game's own guest gun reads it, Modern Warfare 2's
  first, then Call of Duty 4's (`guest::HMW_ORIGINALS`, `hmw_original`),
  then Horizon MW's own HUD icon. Each name carries its game
  (`h1:iw4:weapon_cheytac|iw4:hud_icon_cheytac|hud_icon_cheytac|...`;
  `progression::picture_source`), so a game that is not installed or lacks
  the picture falls through to the next. Originals (Horizon MW gun: MW2,
  CoD4): ak47: ak47, ak47; fal, famas, fn2000, masada, scar, tavor, kriss,
  mp5k, ump45, aug, m240, mg4, sa80, cheytac, m21 (the EBR), wa2000, aa12,
  spas12, striker, ranger, model1887, pp2000, glock, beretta393, tmp,
  coltanaconda, at4, m79: MW2's of the same name only; m16, m4, p90, uzi,
  rpd, barrett, m1014, usp, deserteagle, rpg: MW2's, then CoD4's; m9: MW2's
  and CoD4's `beretta`; ak74u, m40a3, winchester1200: CoD4's (MW2 has none).
  The MORS, the Boomhilda and the M1911 (Black Ops II's model) keep Horizon
  MW's icon. Kill-feed icons are unchanged: the gun's HUD icon
  from its zone (`fastfile_h1::ui_image::read_hmw_icon`). Where the zone
  holds a 1 x 1 stand-in (Horizon MW draws MWR's picture of that name), it
  is taken from the install's `zone/common_mp.ff`. The HUD's kill icons
  come from the same reader.
* **Camos:** the guest-camo wrap covers every non-Black Ops II gun model,
  so Black Ops II's, MW2's, MW3's and Black Ops' camos apply to these.
* **Bots, Mystery Box:** the Box takes them as any guest gun
  (`zm_box_guns`, after the other games: a family the others gave is not
  given again); its Pack-a-Punch is made Black Ops II-style. Bots get guest
  guns only through the mod's swap (`bot_mod_gun`), as for AW's.

### Gun materials: what the game's pixel shader does with the pictures (2026-10-27)

Read from the shader itself: Horizon MW's weapon zones carry their own
techniques and DXBC programs (`hmw_smg`: 28 technique sets, 368 programs;
`h1_tech <zone.ff> <technique> --dump <dir>`, then `vkd3d-compiler -x
dxbc-tpf -b spirv-binary` and `spirv-cross`). The lit gun technique
`opl_lprobe_lmpb_nc_dc1dn1ds1dg1dna1_nofog_r0c0n0s0om0_sm_ld1` runs
`lpo_sm_nofog_dc1dn1ds1dg1dna1_lmpb_l0d_l0sd_r0c0n0s0om0_nc`. Its texture
registers, by the name hash the technique's argument table gives:

| reg | slot (hash) | use |
|---|---|---|
| t4 | `colorMap` (a0ab1041) | `albedo0 = tex.rgb ^ 2` (no tint, no scale constant) |
| t2 | the `_m` picture (bae31156) | `.x` is the camo mask |
| t3 | camo colour (27568b1f) | `albedo = mix(albedo0, camo.rgb ^ 2, mask * camo.a)` |
| t5, t6 | camo normal (5a7d8971), camo specular (cc382e3a) | mixed in by the same weight |
| t9 | `normalMap` | `.xy` signed, z rebuilt |
| t10 | `specularMap` | `F0 = tex.rgb ^ 2`, gloss in alpha |
| t11 | `occlusionMap` (6001f931) | `occ = tex.x ^ 2`, scales the specular and reflection only |
| t0 | `envBrdfLut` | split sum, as the world shader |
| t12 | model lighting volume | ambient (rgb) and the sun's baked visibility (a) |

Out: `albedo * (1 - F0) * (ambient + sun * N.L * shadow) + occ * (F * sunspec
* shadow + reflection * (F0 * lut.x + lut.y))`. The Fresnel is `F0 + (cb3[0].y
- F0) * (1 - |V.H|)^cb3[0].z`, with `envMapParms` (`.y` the maximum, `.z`
the power): `(0.04, 1, 5, 1)` on the camo-capable materials, `(0.33, 1.3, 1.5,
1.23)` on the plain ones (magazines): our shader uses the first for all.

What the probe `h1_gun_tex` (`<retail zone dir> <gun substr> <zone.ff>`;
`H1_BLOCKS=1` also prints the first raw blocks) shows for the AK-47
(`hmw_ar1`): the colour picture is the right one (`colorMap`, inline, one
level, full size, BC3), decodes as stored (the raw block endpoints
are 0x0841 / 0x0000: red 1 of 31) and is simply **very dark**: mean 4 to 15,
maximum 5 to 36 of 255, i.e. an albedo of 0.0003 to 0.02 after the shader's
square. Gained up eight times the stock, grip and handguard maps show a
brown, desaturated wood hue and the receiver a cream-and-green wear
pattern, so they are real, painted pictures at about a tenth of the usual
brightness (AK74u wood 33 to 53, MWR's own M79 wood 49, SCAR stock 85).
The `_m` pictures are camo masks (the AK-47's receiver 255, every other part
0; the AT4's are 2048 x 2048 constants), the three `camo_*` pictures the
zone holds are 1 x 1 red stand-ins the game replaces at run time. The vertex
colour is white (255 on every vertex of the AK74u). So nothing in how we
bind, decode or square the pictures differs from the game's shader; a
near-black albedo leaves the gun to its specular and reflection, which is
the grey the player sees.

## Game side (`assets::lane::h1_map`, `assets::lane::h1`)

A match on `h1:<map>` loads the zone through `load_h1_world` (dispatched
by `match_walk` on `legacy_game_for_path` = `h1`; also `check_map` /
`CodLegacy check-maps`, `build_map_pack` / `CodLegacy pack`). Black Ops II's rules
attach as for Ghosts (Infinity Ward entities, IW surface list); the
master asks no content flag for `h1:` maps.

* **World:** Ghosts' path. Vertices to CoD4's form, the IW3 world builder,
  fallback draw. Sky, tools, shadow-only, distortion and exposure-portal
  surfaces are hidden. Brush models placed by their `script_brushmodel`
  entities are moved (only the vertices the surface's triangles use: H1's
  surfaces share their block's range).
* **Materials (`H1Builder`):** world materials by their `wc_l_sm_*` names
  (Ghosts' rules), model materials by `m_`/`mc_` names. Pictures come from
  the zone, `<map>.pak` (index 96; found beside the file a link points
  to), the retail `imagefile<N>.pak`s, and for a picture or material the
  zone only names, the zones beside it and the shared zones
  (`shared::retail_zones`: `patch_<map>`, `techsets_<map>`,
  `patch_common_mp`, `techsets_common_mp`, `common_mp`, the core zones,
  `code_post_gfx_mp`, then Horizon MW's `hmw-mod/zone/hmw_*.ff`), only
  what the world and placed models use (*Retail maps*). A picture a
  definition names is the map's own first. Those zones are read only when
  the map names something it does not hold (a retail map always does; the
  two usermaps never), and the result is kept for a reload of the same map
  only. A hidden surface's kind (sky, tools, shadow only, ...) is read off
  the definition's technique set. The install's `zone/` is the map's own
  folder for a retail map, else up to four folders above the map (a
  usermap is two levels down), else the `mwr` game folder. Anything
  missing draws grey; the `h1 colour maps` line counts the materials whose
  colour map is drawn, bound to a picture in a pak not installed, or
  missing (and why); nothing missing is fatal.
* **Compass:** the `compass_map_<map>` material's picture, decoded and
  handed to Black Ops II's HUD under that name (as a Black Ops III map's,
  `t7_fx::set_pending_compass`); corners from the `minimap_corner`
  entities.
* **Lighting:** `fastfile_h1::map::iw3_lightmap` converts R8 or BC4 primary +
  RGBA16F secondary (two stacked pages) to CoD4's L8 + A8R8G8B8 under an
  exposure taken from the baked light (Ghosts' rule: 90th percentile to
  0.3). The sun is the ComWorld's first sun light. A placed model uses
  its own ground lighting (flag 0x20) if it has it; the rest (light-grid
  lit) take the middle ground-lit value. The sky is the world's first
  cube sky image (six faces in one image). In the native renderer
  (`render_h1`) the sky is MWR's own technique scaled by the eye's clip
  map stage (`HDR_STAGE_PARMS`, read from the executable:
  `docs/H1_NATIVE.md` *Sky, stages, probes, model lighting and sun
  shadows*). Fog comes from
  `maps/createart/<map>_fog.gsc`, film from `vision/<map>.vision`.
* **Collision:** the clip map through the IW3 clip builder (brushes with
  their indexed planes, terrain triangles with their vertex segments,
  brush models). Placed models (`cStaticModel_s`) are kept beside it for
  the model trace only, as the game does (read from its executable,
  `docs/H1_NATIVE.md` *Collision*): bullets and sight lines meet each
  model's collision LOD triangles, the player's box never does (the map's
  clip brushes stand round props). Until 30 Oct they were triangles
  appended to the world mesh (with a 1.5 M budget Shipment went over).
  Spawn records
  over nothing are dropped, as on Ghosts.
* **Entities (30 Oct):** the text goes through the exe's map-load spawn
  rules and the start scripts' deletions (`fastfile_h1::spawn`,
  `BO2MP_H1_MAP_LOGIC=0` off), and the retail keys the spawn functions ask
  for are named (`dmg`, `wait`, `health`, `northyaw`, ...): see
  `docs/H1_NATIVE.md` *Map logic*.
